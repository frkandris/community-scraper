# Public Listing Widgets

*Every list on the public site is alphabetical and filterable through the same widget, so learning one page teaches all of them.*

## Pieces

| File | Role |
|---|---|
| `scraper/web/static/js/listing.js` | `MpText`, `MpAutocomplete`, `MpListFilter`, and the auto-wiring pass |
| `scraper/web/templates/_listing_filter.html` | The `filter_bar()` macro rendering the markup those widgets bind to |
| `public_base.html` `<style>` block | Widget CSS |

The script is loaded once in `public_base.html` with `defer`, so it runs after
parsing but **before** `DOMContentLoaded`. Page scripts that want
`MpAutocomplete` must therefore live inside a `DOMContentLoaded` handler — an
inline `<script>` in the body runs *earlier* than a deferred external one.

## MpText.norm

The shared comparison key: lowercase, NFD, combining marks stripped, plus a few
non-decomposing folds (ß→ss, ø→o, ł→l). `szentendré`, `Szentendre` and
`SZENTENDRE` all collapse to `szentendre`. `MpText.initial()` derives the A-Z
bucket from it, so accented names group under their base letter and anything
non-alphabetic lands in `#`.

This is the client-side sibling of the server's
[[unicode-safe-identity-keys]] — the same principle, different consumer.

## MpAutocomplete

Used by the home-page city field. Renders its own panel rather than relying on
`<datalist>`, which iOS Safari does not implement at all — the cause of
[[2026-08-mobile-city-search-datalist]]. It forces `autocapitalize`,
`autocorrect` and `spellcheck` off, sizes rows at 44px for touch, and commits a
choice on `pointerdown` so the pick survives the input's `blur`.

`resolve(value)` is the validation entry point: exact normalised match, else a
*unique* prefix match, else a *unique* substring match, else `null`. Callers
should block only on `null` — a stricter guard than the picker can help the user
satisfy is what broke mobile search in the first place.

## MpListFilter and auto-wiring

`filter_bar(t, target='#some-list')` renders a `[data-mp-filter]` block; the
script finds every such block on `DOMContentLoaded` and binds it to the element
named by `data-target`. Listing pages therefore carry **no JavaScript of their
own**. Items opt in with `data-name="Real Name"` — the raw name, since `norm()`
does the folding and the A-Z bar needs the original first letter.

Optional `data-group` names a wrapper (a city section) that hides itself once
all of its items are filtered out.

`MpListFilter.rescan()` re-reads the DOM and rebuilds the A-Z bar. A page that
appends items after the initial attach **must** call it, or the filter keeps a
stale item list and whole letters go missing from the bar.

Two traps this design walks around:

- **`hidden` alone does not hide a Tailwind element.** The UA `[hidden]` rule is
  element-level and loses to any `display` utility class on the same node, so
  `public_base.html` declares `[hidden] { display: none !important; }`.
- **The explore page has a second filter.** Its topic chips hide cards with an
  inline `style.display`. The two compose as an AND (the `!important` rule
  wins), and the widget's visible-count skips items the other filter hid, so the
  number matches what is on screen.

## Server-rendered vs. client-built

`public_cities.html` splits its list: cities **with** content are server-rendered
as real `<a>` elements (they carry the internal linking the page exists for),
while empty ones ship as compact JSON in a `<script type="application/json">`
and are built with a `DocumentFragment` on `DOMContentLoaded`, followed by
`MpListFilter.rescan()`.

The reason is weight. At ~3.8K cities, server-rendering every empty one cost
1.3 MB of markup, and the Tailwind CDN JIT scans the **whole initial DOM** before
the page paints — the same trap [[tailwind-cdn-jit-large-lists]] describes for
admin pages. The JSON form is ~35 bytes per city instead of ~250, taking the page
to 183 KB. Nothing crawlable is lost: empty cities were already non-links, by
the thin-page policy in [[indexing-strategy]].

Class strings in the client-side builder are **full literals**. A computed
`bg-${c}-100` would never be generated by the JIT.

The home page applies the same weight discipline: one `_CITY_DATA` list with
short keys (`n`/`s`/`c`, plus `lat`/`lng` where known) feeds both the search box
and the "cities near you" panel. They used to ship as two JSON blobs holding the
same cities under different key names — 214 KB of a 242 KB page. The merged form
takes the page to 112 KB.

## Where it is used

`public_cities.html`, `public_venues.html`, `public_people.html`, and
`public_explore.html` (both the community grid and tag results). All four now
sort alphabetically server-side — a popularity ordering makes an A-Z bar
meaningless. See [[adding-city-topic]] when adding a page that lists things.
